## 4. 三个反复出现的教训

1. **认不出的页面不要兜底点按钮。** 两次严重翻车（游戏厅、误点出行）都是兜底逻辑太主动。
2. **文字指纹不够用。** 艺术字/无标题页必须靠图像特征（黄卡片、胶囊、卡片边框）。
3. **不要相信自己的推测。** 训练项名、地点名、队友/器材归属，全部以真实截图为准；自己编的权重等于给玩家埋雷。

## 6. 训练项打分为什么一直做不出来（2026-11-23 查清）

### 原来的假设

玩家口述 + 早期录屏（`demo/montage/cards_464.png`）看着像这样：

- 队友 = 球场上站着的角色名标签
- 器材 = 画面中间那排卡片
- 金光 / 彩光 = 卡片外框光效

于是 `_score_core` 写成 `队友数×1 + 金卡×1 + 彩卡×1.5`。

### 真机上是什么样

写了 `CoreSweepTask`（点一个训练项连拍 14 帧，逐帧 OCR）实测：

1. **这页一张卡片都没有。** 那批黄框卡片（球鞋 / 立绘，右上角带靴子/握手/盾牌角标）
   只在**点完「决定」后的开训动画**里出现 —— 也就是说，它是你选择的结果，不是选择依据。
   `find_cards()` 在训练项页恒返回 0 张，`equipment` 那一项永远加 0 分。
2. **球场上确实有队友，但只在选中某个训练项之后才出现**，而且各技能不同：
   投射会站真崎+百目鬼，弹跳站佐久间，运控/防守/意识可能一个人都没有。
3. **「球队经理」每场都在**，是场边角色，不是队友。
4. 过渡的那 1 秒里 OCR 会把相邻两个名字粘成一个框，队友数在 0~3 之间乱跳。

结论：原来 4 项权重里有 3 项拿不到数据，剩下的「队友数」还被粘连和经理污染 →
6 个训练项得分几乎全 0 或全相等 → 排序退化成「按 y 坐标选第一个」，
看起来就像「打分没生效」。

### 现在的打分

```
score = 队友数 × 1.0 + 训练项等级奖励(Lv.1=0 / Lv.2=0.5 / MAX=1.0)
score *= (1 - 失败率/100 × fail_weight)      # 失败=白扔体力，按比例打折
```

只用三个**真机上确实可读、且各技能确实不同**的信号：出场队友数、训练项等级、失败率。

读取方式：点开训练项 → 等 0.9s → 连拍 5 帧（每帧 OCR）→
队友名出现 ≥2 帧才算、失败率取众数、等级取众数。

实测日志（2026-11-23 05:24）：

```
「弹跳」LV.1 失败率=0%  队友1['佐久雅']        → 得分 1.00
「防守」LV.1 失败率=0%  队友1['闪堂']          → 得分 1.00
「运控」LV.1 失败率=0%  队友2['百目鬼','真崎'] → 得分 2.00   ← 选中
「防守」LV.1 失败率=28% 队友1['百目鬼']        → 得分 0.72   ← 失败率打折生效
「体能」LV.1 失败率=28% 队友2['闪堂','真崎']   → 得分 1.44
```

### 仍然不够好的地方

- 「佐久雅」这种是「佐久间」的 OCR 误识，数量对、名字错，暂时不影响打分。
- 队友多的技能是否真的收益更高，**玩家还没确认**。现在只是按「多一个队友多一份加成」推断，
  权重 1.0 随时可以在 `strategy.yaml` 的 `tuning.core_score` 里调。
- 如果以后发现器材真能提前看到（比如某个页面有预览），把 `equipment` 权重改回非 0 即可。

- 「休息」到底恢复多少精力仍未确认（文档写「不消耗精力，推进一天」）；目前策略是

## 8. 局外体力溢出 + 出行挑错档（2026-11-23 06:43 玩家现场发现）

### 8.1 「我的局外体力为什么溢出这么多」

**根因：补药逻辑不看剩余空间。**

三个叠加的毛病：

| # | 问题 | 后果 |
|---|---|---|
| 40 | 早期按「点了几次」计瓶数，不看专注实际涨没涨 | 06:01 那轮从 11/150 连喝 4 瓶 ×60 = 240，上限只有 150，**白扔一百多点** |
| 41 | 改成按涨幅计数后，仍然闭眼点最下面那行（大瓶 +60） | 只差 20 也喝 +60，每瓶浪费 40 |
| 42 | `stamina_refills` 是**整轮累计**，`每轮最多补专注次数=4` | 一轮 7 周只有 4 瓶额度，喝完后整轮不再补，后面训练开不了 |

修法（`_do_focus`）：

```
缺口 = 上限150 - 当前专注
缺口 ≥ 60   → 喝大瓶 +60
30 ≤ 缺口 < 60 → 喝小瓶 +30
缺口 < 30    → 一瓶都不喝，先关窗试训练
                （同一处反复弹窗 2 次才认，改喝最小瓶）
缺口 ≤ 0     → 直接关窗
```

- 「专注+N」按 **y 坐标**配对到同一行的「使用」按钮，所以不会误点到钻石那行
  （钻石行的按钮文字是价格「50」，本来也不叫「使用」）。
- 读不到数值时按缺口 30 兜底 → 只会选最小瓶，绝不会再灌 +60。
- `stamina_refills` 改为**每次弹窗**计，`close()` 时归零。

### 8.2 「差 21 点却选了 +70，而不是 +30 加属性」

**根因：拿标签上的原始数值当收益，没做溢出截断。**

旧逻辑 `eff = 标签值`（+70 → 70 分），所以 +70 永远赢；而玩家要的是
**能真正吃进精力条的部分**才算收益。现在统一走 `_reward_key`：

```
有效精力 = min(标签精力值, 130 - 当前精力)
优先级   = 笔记 > 训练项 > 有效精力 > 属性 > 零用钱
```

实测（缺口 21）：

| 选项 | 元组 | 数值 | 结果 |
|---|---|---|---|
| 野餐 精力+70 | (2, 21, 0, 0) | 20210 | |
| 划船 精力+30 属性+20 | (2, 21, 20, 0) | **20230** | ✅ 选中 |
| 散步 零用钱+ | (0, 0, 0, 1) | 0.1 | |
| 读书 笔记+1 | (4, 0, 0, 0) | 40000 | 最高 |
| 特训 技能+1 | (3, 0, 0, 0) | 30000 | 次高 |

顺带修掉：OCR 常把数字读丢，只剩「精力++」/「精力+」。原来 `_gain` 一律返回 1，
三档全打平 → 按坐标瞎选（日志里 06:20–06:26 全是「标签『精力++』精力+1」）。
现在按加号个数还原档位：单加 30 / 双加 70（属性 20 / 40）。

### 8.3 覆盖到的三处入口

`_do_trip`（地图）、`_do_go`（前往XX 列表）、`_score_option`（事件黄卡）
全部改为同一套 `_reward_key`，不再各自维护权重表 —— 之前就是三处各写一套，
改了一处漏了两处。

### 8.4 补记（06:49 玩家给出关键背景，推翻了「补满」的做法）

**玩家原话**：「那个电池一样的 202/150 就是体力啊，已经溢出到 202 了。
小瓶回 30，大瓶回 60。**每一次训练也只会消耗 30**。」

三件事一次说清：

| 事实 | 带来的改动 |
|---|---|
| 体力**允许溢出**，顶栏显示 202/150 | `_parse_ab` / `_read_stamina` 里的 `a <= b` 校验必须删掉，否则溢出值整条被丢 |
| OCR 吞斜杠时 `202150` 会退化成 `(20,150)` | 放宽到 `a <= cap*2`，`202150` 正确还原成 202 —— 这个误读正是「以为不够 → 又去补 → 越补越溢」的闭环 |
| 一次训练**只消耗 30** | 补药目标从「补满」改成「够 30 就停」，要补只喝小瓶 +30 |

`_do_focus` 现在的判定顺序：

```
读得到体力数值：
   a > 150（已溢出）或 a = 150  → 关窗，一滴不补
   a >= 30（够一次训练）        → 关窗，一滴不补
   a < 30                       → 喝小瓶 +30（小瓶没库存才喝大瓶 +60）
读不到数值：保守按「不够一次」处理，只喝最小瓶
```

这也解释了之前日志里 `局外专注 None/None`：不是 OCR 读不到，是读到了 `202/150`
又被 `a <= b` 判成非法值扔掉了。

### 8.5 第三次修正：读不到体力，根因在 OCR 文本长得不像规范数字

06:50 探针把大厅顶栏原样打出来，是这样：

```
「221/150+ü三」@(1564,48) w=580 h=45
```

两个坑叠在一起：

1. **正则锚定了结尾**：`^(\d{1,3})/(\d{2,3})\+?$` 要求以最多一个 `+` 结束，
   实测尾巴是「+ü三」，直接不匹配 → `_parse_ab` 返回 None → 体力永远读不到。
   改成 `re.search(r"(\d{1,3})/(\d{2,3})")`，不管后面粘了什么。
2. **不校验上限就认**：放宽之后页面上随便一个 `218/271`、`303/164`
   都被当成体力写进 `out_focus`，日志里 `221/150` 和 `303/164` 交替出现。
   新增 `_ab_kind(a, b)`：只认 `b` 贴着 150（±8）或 130（±8）的，
   其它一律 None。

同时把精力的上限固定成 130 常量，不再用读到的 `b` —— OCR 读到 134 时，
`if b > stamina_max` 的写法会让上限定死在 134，之后读到真正的 130 反而更新不了，
当前值就冻结在 108 不动（06:51 实测）。

验证（06:52 实跑）：

```

第 7 步  每日页   精力 90/130
第 9 步  训练项页 精力 44/130       ← 训练消耗后正常刷新
第 75 步 训练项页 精力 88/130
```

## 12. 选人页「没选满就停」+ 工作台（2026-11-23 09:00）

### #52 空白加号 = 还有东西没选，必须停下来

选人三连（选择队友 / 选择笔记 / 选择器材）里，**没选的槽位长这样**：

```
金色粗边框 + 近白底 + 中间一个黄色十字
```

器材页实测坐标 (0.555, 0.640)，尺寸约 187×181（1920×1080 下）。
已选中的卡片刚好相反：整块金黄、饱和度很高、里面是图标和「50」这种数字。

**判定条件（四条同时成立才认，缺一不可）**：

| # | 条件 | 阈值 |
|---|---|---|
| 1 | 金色描边轮廓，高度落在区间内 | `0.09H ≤ h ≤ 0.24H` |
| 2 | 接近方形 | `0.72 < w/h < 1.35` |
| 3 | 轮廓填充率够（是实心框不是碎金片） | `area/(w·h) ≥ 0.35` |
| 4 | 内部中间 46% 区域是近白 | 近白占比 ≥ 0.55 |
| 5 | 内部还留着黄色十字 | 金色像素占比 ≥ 0.08 |

**为什么不用 OCR**：这个「+」onnxocr 完全读不出来（跟公告页的关闭 × 一个毛病），

### #53 训练项读数「6 帧只用得上 2~4 帧」（玩家：是不是加个延时，别急着拍）

**现象**：日志连续出现 `训练项读数 4/6 → 2/6 → 0/6 帧可用`，最后一个训练项常常 0 帧，
于是 `全部训练项读数都失败，按当前默认项决定` —— 「挑最优训练项」有一半次数在空转。

**根因（两条叠加）**

1. 点完技能只等 0.9s 就开始连拍，而点开的过渡动画约 1 秒，前几帧全是动画中间态：
   名字标签还在淡入、训练项详情没展开 → 被判「不像训练项页」扔掉。
2. 判定本身太严：要求右侧**至少认出 2 个训练项名**，可面板一展开就把右列盖住了，
   `hits` 掉到 0~1，正常帧也被判废；废帧还占「6 帧」的配额，越到后面的技能越惨。

**改法（第二版，实机打回过一次）**

- 第一版按玩家建议「先等 1.2s 再拍」，结果**更差**：10:05 那轮三个训练项全是
  「6 帧有效但读不到任何数据」——等到的是浮层收走之后的空页面。
  CoreSweepTask 05:14 的结论才是对的：加成浮层只存在 **1~2 秒**。
- 定稿是「**早拍、密拍**」：`_sample_core(warmup=0.15, gap=0.18, frames=10)`，
  调用处不再额外等待；覆盖 0.15~1.95s 这个窗口。
- 废帧**不占配额**：`while used < 10 and tries < 14`，避免中途帧把配额吃光。
- 判定放宽：训练项名 ≥1 / 有「失败率」/ 有 Lv·MAX / 场上 ≥2 个队友名，任一命中就算有效帧。
- 凑够 3 帧失败率 + 3 帧名字就提前收工；日志 `训练项读数 N/10 帧有效（试了 X 次）`。

**顺带定的三条口径（玩家 2026-11-23）**

- 训练项等级**不参与计分**：`level_bonus` 三档全 0，仍读出来打日志。
- 失败率仍是**乘法折扣**：`分 ×(1 - 失败率/100)`，30% → 打七折、50% → 打五折。
- 失败率**全部** >30% 且商店确认没有精力道具 → 强制改练「意识」（成功率最高）；
  有技能没读到失败率、或本期没进过商店 → 这条不生效，按原排名。

单测：`tools/test_core.py`（计分 4 条 + 风险规则 6 条，全过）。

`assets/anchors.json` 的页面键、`config/states.yaml`、`config/strategy.yaml`、4 份任务配置同步。
游戏 OCR 原文（`请选择一种加强训练`、`加强训练成功`、`确认编队`、`请选择1个技能`）一律**不动**。

### #63 读数 0 帧不再「蒙着继续」：停机 + 弹窗 + 截图（2026-11-26）

**玩家问**：「为什么采样 0 帧这么多还继续？应该停下来，你找到原因，再看。而不是一股脑流过去。」

等于拿游戏默认项蒙一把，还把这一天白走完。

**改法**：新增 `_read_fail_stop_now(name, detail)`：

1. 截图 `screenshots/auto/read_fail_<训练项>_*.png`；
2. 桌面置顶弹窗（写明原因 + 该看什么）；
3. `read_fail_stop = True`，主循环 `_run_loop` 在「训练项页」分支看到这个标记就 `break`（停机），
   不再排名、不再点决定。

接入三个口子：单项 0 帧、全部候选都读不到、全部读数失败。
开关 `读数失败即暂停`（默认 **True**，写在 `configs/AutoTask.json` 与 `strategy.yaml` 的 tuning 段）；
关掉才退回旧行为（排除该项按默认项走）。

**验证**：单测两例（默认 → `read_fail_stop=True` 并弹窗；开关 False → 只警告继续）；
`py_compile` 全绿；配置 JSON/YAML 全部可解析；`anchors.json` 页面键与代码一致（不一致数 0）。
**未实跑**：等玩家打开游戏再跑一轮看「读数失败」是否掉到个位数。

### #65 默认项认成「体能」→ 把「投射」当普通项点开 = 直接开训（2026-11-26）

**现象**：11-26 10:53 实跑，点开「投射」后画面直接跳剧情。
日志原话：

```
当前默认选中「体能」→ 这一项全程不点击，直接采默认帧
接下来点开 2 个带角标的训练项：[投射, 意识]
```

玩家当场指出：「不要点投射，因为默认就是投射。」

**根因**：`_selected_skill` 用「六项里底色最暗（亮度<155 且 B-R<60）」判断哪个是
游戏默认选中项。这个判据是 11-23 用两帧截图凑出来的。11-26 这轮六项里「体能」
那格更暗，于是判给了体能 —— 真正的默认项「投射」被当成普通项，点开一次。
**点默认项 = 确认开训**（3~4 秒后直接跳训练结果），这次训练项比较整体作废。
更糟的是原来的兜底：认不出默认项时「所有带角标的项全点开」，等于一次误判必踩雷。

**改法（玩家定版 A：写死）**：

- 新增类常量 `DEFAULT_ITEM = "投射"`，`selected` 直接读它，**不再用颜色做决策**；
  颜色识别降级为对账日志：`颜色识别猜「体能」，但按写死的默认项「投射」处理`，
  以后游戏若改了默认项，这行日志能第一时间发现。
- 第二层一起改（认不出就不许蒙）：
  - 默认项在画面上但**没角标** → 今天没人站台，跳过它，点其余项（切换选择，安全）；
  - 画面上**读不到默认项这一行**（坏帧/残帧）→ 一个都不点，截图 + 弹窗 + 停机；
  - 训练项页**连六项都读不全** → 同样停机，不再 `_decide()` 点决定。
- `_read_fail_stop_now` 加 `hint` 参数，三种场景弹窗说人话（读数失败 / 认页失败 / 读不到默认项）。

**实跑验证**（11-26 11:02–11:18，510 步，1 轮）：

|---|---|---|

| 颜色识别结果 | 体能（错） | 仍是体能，但被忽略 |
