# 01 架构设计

## 1. 分层

```
┌─────────────────────────────────────────────────────────────┐
│ 执行层   Pynput 真实鼠标 / 键盘（必须前台）                    │
├─────────────────────────────────────────────────────────────┤
│ 决策层   候选动作 → 规则打分 → 选一个（config/strategy.yaml）  │
├─────────────────────────────────────────────────────────────┤
│ 状态层   页面指纹匹配 → 当前状态 ID（config/states.yaml）      │
├─────────────────────────────────────────────────────────────┤
│ 感知层   WGC 截图 → OCR 文字框 + 图像特征（颜色/形状/位置）    │
└─────────────────────────────────────────────────────────────┘
```

一层只干一件事。现在代码里这四层都有，但**状态层还是 if-else 硬编码**（`AutoTask.PAGE_RULES` + `_do_xxx` 方法），
`states.yaml` 是建议的目标形态，见 §5 演进路径。

## 2. 状态机模型

一个状态 = 一个页面；一条边 = 一个可点按钮。

```yaml
states:
  <state_id>:
    name: 中文名
    anchors: [出现即判定为本页的字符串/特征]     # 从上往下匹配，先命中先用
    wrong_anchors: [出现就说明不是本页的串]      # 排除误判（可选）
    actions:                                   # 可点的东西
      - label: 按钮文字或图标描述
        kind: text | badge | card | anywhere    # 怎么找它
        target: <下一个 state_id>               # 点完会去哪
        guard: 什么时候该点（引用 strategy.yaml 的键）
        cost: 花不花资源（精力/钱）
    fallback: pause | click_center | first_action
```

判定一个状态必须**唯一**且**可证伪**：录屏里真实出现过的字才算锚点。
反例（都真踩过）：

| 错误的锚点 | 为什么错 |
|---|---|
| 「赢得比赛」 | 是每日页常驻 HUD，每页都有 |
| 「新品上市」 | 主界面也有这个入口 |
| 「训练事件」 | 事件页**根本没有**这四个字（只有对话框 + 底部卡片） |

## 3. 决策链

状态确定后，并不是「有一个按钮就点」：

```
候选动作 = 该状态 actions 里 guard 成立的那些
   ↓
打分（规则来自 strategy.yaml）：每个动作给出一个分数
   ↓
排序（分数 → 平局规则 → 兜底顺序）
   ↓
执行 + 记录日志（为什么选它）
   ↓
等待页面变化（超时 → 重新判状态，而不是重复点）
```

### 训练项页的例子（已实现，是本项目最复杂的一处决策）

```
对每个「带角标的」训练项条目：
    点开它  →  等 1.2s  →  读屏
      队友数 = 球场上名字标签数（去掉主力「希雅」）
      器材数 = 画面中间那排卡片数
      光效   = 每张卡外框色相分布：单色橙黄→金 / 多色相→彩
    得分 = 队友×1 + Σ(金光1 / 彩光1.5 / 普通0.5)
按得分降序，同分比失败率（低者优先）
点回最优技能 → 点「决定」
```

## 4. 三层配置

| 文件 | 管什么 | 谁改 | 改动频率 |
|---|---|---|---|
| `config/states.yaml` | 页面结构：有哪些页、页面之间怎么跳 | 开发者（跟着游戏版本走） | 低 |
| `config/strategy.yaml` | 策略：选哪个、阈值多少、优先级顺序 | 玩家 | 高 |
| 任务 `default_config` | 运行参数：等待秒数、最大步数、兜底开关 | 玩家 | 中 |

玩家改行为只碰 `strategy.yaml`，例如：

```yaml
core_score:
  teammate: 1.0        # 队友每人 1 分
  equipment_gold: 1.0  # 金光器材 1 分
trip:
  priority: [笔记, 公园]
  exclude: [游戏厅]
```

## 5. 演进路径：从 if-else 到数据驱动

现在（v0）：

```
AutoTask.run()
  page = _classify(items)          # PAGE_RULES 字符串匹配
  if page == "训练项页": _do_training_core(...)
  elif page == "出行":  _do_trip(...)
  ...
```

目标（v1）：

```
machine = StateMachine(config/states.yaml)
page = machine.match(items, frame)         # 锚点 + 图像特征
acts = machine.actions(page)               # 该状态的动作表
best = policy.choose(acts, ctx)            # strategy.yaml 打分
execute(best) → wait_change() → loop
```

迁移方式（不推倒重来）：

1. 把 `PAGE_RULES` 搬进 `states.yaml` 的 `anchors`（纯搬运，零风险）。
2. 每个 `_do_xxx` 拆成「候选动作列表 + 打分函数」两段，`_do_xxx` 只剩编排。
3. 逐页替换，每换一页用 `CheckTask` 回归一次，确认判定不变。
4. 全替换后再删 `PAGE_RULES`。

**在此之前不要动主流程**：现在能跑通的部分（每日页 → 训练 → 决定）都很脆，重写容易把已验证的路径弄坏。

## 6. 失败处理原则

| 情况 | 行为 |
|---|---|
| 认不出页面 | `pause` + 通知，日志打全部 OCR 文字 + 存截图 |
| 主按钮是灰的（未选人） | 不点，`pause` + 通知 |
| 进了小游戏 | 找「放弃」→ 处理二次确认 → 校验是否真退出；连续 5 次失败才 pause |
| 连续 N 步页面没变化 | 重判状态，不重复点同一个位置 |
| 数值跳变（OCR 抖动） | 沿用上一帧值（`value_jump_limit`） |

## 7. 线程/时序约束

- 单线程顺序执行，不做并发点击。
- 每次点击后必须 `等页面稳定`（当前 1.0~1.3s），不能连点同一个位置。
- 取帧用 `next_frame()`；`nullable_frame()` 只返回缓存，会导致「一直拿到同一张图」。
- 框架窗口一旦跑出屏幕会自动 `executor.pause()`，取帧时遇到要显式 `executor.paused = False`。
